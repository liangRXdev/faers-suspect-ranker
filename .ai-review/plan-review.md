**結論：v0.1 尚不宜動工。主要阻擋點是 D3／D4／A9 將「文字配對成功」當成「已確認目標單方」，且允許已知誤判繼續進分母，與本案最重要的安全邊界衝突。**

本次僅審規格並唯讀核對現況，未修改檔案、未執行測試或重新進行 §4 的 live 抽樣。不將雙引擎、逐列載入、角色優先順序、少量樣本顯示比例等既定取捨列為缺陷。

## 1. 需求與邊界缺漏

### 1.1 **Blocker / 單方辨識的成功條件與安全前提衝突 / 會把錯誤計算與錯誤測試一起固定下來 / 分開定義「候選文字命中」與「可納入分母」**

涉及 D3、D4、A9。

- token-phrase 只能證明文字關係，不能證明同一有效成分。例如合成反例：查詢 `INSULIN`，條目為 `INSULIN GLARGINE`；符合連續 token，卻不能僅因此認定為同一目標成分。
- 合成反例：`generic_name` 陣列分別放 `AMOXICILLIN`、`CLAVULANATE POTASSIUM`。D4 的「任一元素含分隔符」不成立，仍可能當成單方。
- 去除所有括號會同時刪除劑量描述與成分資訊。例如 `AMOXICILLIN (WITH CLAVULANATE POTASSIUM)`，依現行規格會刪掉複方證據。
- A9 明文允許「規則判錯則斷言目前行為並寫成限制」，因此即使確認把複方當單方、不同成分合併，也能驗收。

**晚修成本：** 必須重訂辨識契約、分類預期、兩端測試與 methodology；若已使用，還須解釋過往比例何以改變。

**建議修法：** 規格先定義哪些證據足以確認目標單方；資訊不足、互相矛盾或身分仍有歧義者不得進 valid。A9 應區分：

- 保守排除造成的漏配：可作已知限制。
- 已知誤合併、複方誤納入：必須修正驗收預期，不得用文件豁免。

這不要求 RxNorm、商品名展開或新增資料源，與 N7 相容。

### 1.2 **Medium / D4 的欄位分支未封閉 / 兩端會各自補出不同規則 / 明列各種欄位存在組合及分類結果**

D4 只有「有 generic_name」與「無 openfda」兩條路，漏掉：

- 有 `openfda.brand_name`，但沒有 `generic_name`。
- `generic_name` 為空陣列、空字串或錯誤型別。
- generic 欄位看似單方，medicinalproduct 卻明示複方。
- 複方資訊出現在括號或未列出的分隔形式。

**晚修成本：** 邊界散落於兩套引擎，之後需逐一修正分類與測試。

**建議修法：** 用規格決策表定義欄位缺漏、證據矛盾與無法確認時的歸類；保留 D5 已定案的「已確認單方優先於同報複方」規則。

### 1.3 **Medium / 重繪、換 ADR、逾時後的回寫權限未定義 / 數字可能正確但顯示在錯列 / 明定結果只能更新原查詢身分所屬的目前狀態**

D9 的同鍵合併不足以處理：

1. ADR A 的比例仍在載入。
2. 主分析改查 ADR B，表格重建。
3. A 的結果稍後回來，被寫入 B 的相同列位置。

另一個反例是逾時後按重試，舊請求晚到，覆蓋新請求的結果或錯誤狀態。

**晚修成本：** 要重新整理列 state、請求生命週期與兩版互動測試。

**建議修法：** 明定跨查詢、重繪、逾時及重試的結果歸屬；過期結果不得更新目前列或覆蓋較新的狀態。同鍵仍在載入時重繪，不得新增請求或永久卡住。

### 1.4 **Medium / 60 秒的起訖與適用範圍不明 / 實作完成後仍無法判斷是否違約 / 定義排隊、下載、解析與重試的時間契約**

§7 沒說清楚：

- 60 秒從點擊、出佇列，還是送出 HTTP 起算。
- 是每次嘗試 60 秒，還是含退避與重試的總時間。
- 收到 headers 後，body 一直未完成是否仍受限制。
- GAS 呼叫失敗或逾時如何離開 loading。

**晚修成本：** 測試時計與 UI 文案會建立在不同定義上。

**建議修法：** 明定兩版可觀察的時間上限與狀態終點，並區分排隊與實際載入。不可僅以「fetch Promise 已完成」視為整個回應完成。

### 1.5 **Medium / API 失敗分類與回應結構檢查不完整 / 錯誤可能變成有效的小樣本或永久 loading / 補齊錯誤決策表**

目前未封閉：

- 400、401、403、非 NOT_FOUND 的 404。
- 404 或 5xx 回 HTML、截斷 JSON、JSON 解析失敗。
- HTTP 200 同時帶 `error` 與 `results`。
- `results` 是陣列，但元素為 null、缺少 patient 或 drug 結構。
- 網路錯誤沒有 HTTP status，卻要求「訊息含 HTTP 狀態」。
- 5xx／網路錯誤的退避時間未定。

**晚修成本：** 兩端錯誤處理與重試行為分歧，且可能污染快取。

**建議修法：** 區分請求失敗、回應無法解析、通報可解析但無法對應；逐類定義是否重試、終態與是否可快取。不得默默刪除壞通報後，把剩餘通報當成完整抽樣。

### 1.6 **Medium / API key 的錯誤輸出邊界沒有驗收 / 真正出錯時才會發現憑證外洩 / 將既有機密要求納入失敗斷言**

B6 只驗證 URL 帶 key，B7 未限制 error 內容。網路例外可能包含完整 URL；直接顯示或記錄原始錯誤，可能把 key 帶到畫面、console 或驗收紀錄。

**晚修成本：** 已外洩的 key 無法靠修正畫面收回。

**建議修法：** 使用測試用辨識字串作 key，覆蓋網路、解析、HTTP 與 GAS transport 失敗；斷言使用者訊息、log、回傳內容與驗收紀錄均不含該字串。這是既有威脅模型的驗證，並非新增需求。

## 2. 架構風險

### 2.1 **High / 「15 MB 可處理」尚未成為雙平台可行性證據 / 可能完成後才發現 GAS 路徑不可交付 / 把實際處理鏈列為動工前可行性門檻**

50 MB 是 UrlFetch 回應限制，不能推出「取得文字、JSON.parse、遍歷全部 drug、回傳摘要」必然能在期限內完成。官方另有每次執行六分鐘限制；`limit=100` 限制的是通報數，並不限制每筆 drug 數或回應位元組數。[GAS quotas](https://developers.google.com/apps-script/guides/services/quotas)、[openFDA limit](https://open.fda.gov/apis/drug/event/how-to-use-the-endpoint/)

§4 的 15 MB／5.6 MB 是特定樣本觀察值，不能當作上限，也不能保證 GAS 與瀏覽器使用相同壓縮傳輸。

**晚修成本：** 若不可行，會牽動單次查詢方式、抽樣數與等待契約，是最可能引發架構返工的平台決策。

**建議修法：** 規格要求在實際 GAS 與瀏覽器完成代表性大回應的完整流程，記錄大小、耗時、成功／失敗終態。超出可處理範圍必須明確失敗，不可靜默減少樣本或以截斷結果計算。現有資料不足以宣稱不可行，也不足以宣稱已可行。

### 2.2 **High / 回傳與快取資料模型未包含 UI 必要資訊 / 兩版介面完成後仍需改契約 / 先定義共同摘要契約**

D8 說 CacheService「只存計數」，但 §7.6 要求抽樣期間；只有六類計數無法還原最舊與最新 receivedate。規格也未完整定義兩端共同回傳結構、日期缺漏與 empty 的表示方式。

**晚修成本：** 快取命中時缺欄位，可能被迫重打 API，或兩版顯示不同資訊。

**建議修法：** 將「只存計數」改為「只存計算摘要，不存原始通報」，明列計數、比例、期間及缺漏表示。期間應明定涵蓋全部 sampled 或僅 valid，且冷載入與快取命中顯示一致。

### 2.3 **Medium / 搜尋語意與本地 token-phrase 的等價性未被證明 / 為了降低 unmatched 可能反而放寬到誤認 / 將其定位為保守辨識規則**

openFDA 文件支持 quoted phrase 查詢，但沒有證明其 analyzer 等同「大寫、所有非英數改空白、連續 token 比對」。[openFDA advanced syntax](https://open.fda.gov/apis/advanced-syntax/)

現有 `_clean` 還會移除雙引號與反斜線；D3 未說明本地辨識使用原始名稱還是相同清理後名稱。可核對 [Code.gs:434](/C:/Users/liang/projects/faers-suspect-ranker/Code.gs:434) 與 [docs/app.js:64](/C:/Users/liang/projects/faers-suspect-ranker/docs/app.js:64)。

**晚修成本：** 查詢、本地辨識與快取鍵會形成三套不一致的等價關係。

**建議修法：** 刪除「可找回同一條目」的保證；明定同一查詢文字如何用於三者，並保留 unmatched。快取不得合併尚未證明查詢等價的名稱。E1 的 unmatched 門檻不得成為放寬身分確認的理由。

### 2.4 **Medium / 序列請求不等於節流，GAS 的併發範圍也未定 / 多列操作時才暴露限速與重複請求 / 明定兩版的排程作用域**

D9 只限制 Pages 同時一個比例請求，沒有保證請求間隔；快速失敗也可能連續送出。GAS 不同列則是獨立執行，既有每次執行內的 sleep 不會自動協調其他呼叫。

**晚修成本：** 要重新整理比例請求與重試排程。

**建議修法：** 定義單一頁面工作階段內兩版的佇列、同鍵合併與間隔，重試同樣受約束；不用擴張成跨使用者全域排程需求。

### 2.5 **Low / 平台事實與現況描述有幾處需校正 / 文件會把暫定值固定成外部保證 / 修正文句並保留既有保守設定**

- **無 key 額度：** 官方目前列為每 IP 每分鐘 240、每日 1,000；有 key 每分鐘 240、每日 120,000。§3／§6 的 40 與現有程式及 README 一致，但不是目前官方數值。可保留 1800ms 作本工具保守設定，無須因此改既有分析。[openFDA authentication](https://open.fda.gov/apis/authentication/)
- **GAS timeout：** 目前官方 `UrlFetchApp` 文件列有 `timeoutSeconds`，預設 360 秒；§7 僅列 `muteHttpExceptions`，尚未落實自己的 60 秒契約。[UrlFetchApp](https://developers.google.com/apps-script/reference/url-fetch/url-fetch-app)
- **日期語意：** `receivedate` 是 FDA 首次收到通報的日期；`receiptdate` 才是最近資訊收到日期。保留既定 sort 即可，但「最近通報」與期間應解釋為首次收件日期。[FAERS 欄位文件](https://open.fda.gov/fields/drugevent_reference.pdf)
- **部署 workflow：** 本地基準沒有 `.github/workflows`，因此 §3「僅 GitHub Pages 部署」不宜寫成 repo 內存在部署 workflow。
- **兩次計數請求：** 每藥兩次是冷快取正常路徑；既有快取命中不會送出 HTTP，驗收計數須說明快取初始狀態。

最難回頭的決策依序是：**身分／單方確認契約、共同摘要資料模型、大回應的單次處理可行性**。

### C. 不影響既有行為

- **問題：**
  - GAS 明定不設伺服器 timeout，但錯誤表兩端一致，仍要求「60s timeout 後重試」。
  - B7 要求 GAS 對應 B3，而 B3 描述的是 fetch／body Promise 停滯。
  - GAS watchdog 150s 後，若佇列繼續送下一筆，上一筆伺服器執行可能仍未結束；因此不能同時宣稱實際請求永遠只有一筆。
- **為什麼現在不修之後會更貴：**會讓 controller、傳輸 stub 與實機驗收各自驗證不同事情，全部綠燈卻沒有共同保證。
- **建議修法：**分開寫 Pages 的 HTTP 嘗試期限、GAS 的前端等待期限與晚到丟棄；明定 watchdog 後是否釋放佇列，以及「同時一個」約束的是前端有效工作還是實際伺服器執行。無法取消的 GAS 工作不可宣稱已停止。

### 2.3 Medium／B5 把 Pages in-flight 合併要求套到了 GAS

**位置：**`plan.md:105`–`:110`、`:221`。

- **問題：**D7 只有 Pages 宣告 in-flight Promise 合併；D8 只有 GAS CacheService。快取尚未產生時，獨立 GAS 呼叫並不因 CacheService 而自然合併。
- **為什麼現在不修之後會更貴：**可能為滿足測試額外引入同步機制，或用單一 vm 的假共享狀態偽裝 GAS 執行模型。
- **建議修法：**將 B5 拆成 Pages 傳輸併發合併、GAS 已完成摘要的快取命中、兩版 controller 同 key 不重複排隊。不要額外承諾獨立 GAS 執行之間的 in-flight 合併。

### 2.4 Medium／查詢身分的分隔符可碰撞

**位置：**`plan.md:106`、`:107`、`:111`。

- **問題：**`_clean` 不移除 `|`，因此 `(drug="A|B", reaction="C")` 與 `(drug="A", reaction="B|C")` 得到相同 key。後續 md5 不會消除此碰撞。
- **為什麼現在不修之後會更貴：**會造成快取與列狀態跨查詢共用，直接違反身分隔離。
- **建議修法：**規格要求 key 能無歧義表示兩個欄位；保留已定案的大小寫與 `_clean` 規則，不需要增加名稱正規化。

### 2.5 Medium／位元組上限與解析期限尚未形成可驗證定義

**位置：**`plan.md:122`、`:130`、`:228`。

- **問題：**B9 寫 body「長度」，但 SP_MAX_BYTES 是位元組；未指定壓縮前後、字元或 UTF-8 位元組。60s 又包含解析完成，不能只以 fetch／body 的中止涵蓋範圍代表已驗證解析期限。
- **為什麼現在不修之後會更貴：**兩端可使用不同單位，對同一回應得出不同終態；測試仍可能只用 ASCII 小 body 通過。
- **建議修法：**固定容量單位與量測階段，並明定超限／超時結果不得發布成功摘要。加入多位元組內容、恰等於上限，以及 body 完成後才跨越期限的情境。

## 4. 更簡單的替代方案

### 4.1 Medium／讓 D3 所有列使用同一個「本次查詢的正規化模式」

- **問題：**目前 moiety、不去鹽例外、#3 去 SALTS 與 exact 的規則分散，容易產生雙重解讀。
- **晚修成本：**兩套引擎與人工 fixture 都會各自形成例外。
- **建議修法：**規格先一次定義本列使用的模式，再由所有比較與集合判斷共同引用；只保留必要的 generic／MP 劑量處理差異。無須新增字典、資料源或框架。

### 4.2 Medium／把共同契約限於摘要與使用者可見終態

- **問題：**強求 Pages fetch 與 GAS UrlFetchApp 具有相同 timeout／in-flight 行為，增加不可能忠實模擬的驗收。
- **晚修成本：**測試模型與實際平台分離。
- **建議修法：**共同保留 D5、成功／空／錯誤語意及機密保護；平台各自驗證傳輸生命週期。前端共用 controller 的方向不變，也不需要新增跨執行鎖或全域排程。

### 4.3 Medium／證據不足時直接 ambiguous，優先刪除誤納入路徑

- **問題：**為保留缺 generic 的名稱命中率，規格仍跨越「確認名稱」到「確認單方」。
- **晚修成本：**誤納入一旦成為 golden，後續修正會被視為回歸。
- **建議修法：**在現有資料源與有限字典內無法確認者直接排除，接受較少 valid；同步修正人工裁決案例。這符合既定「不以降低 unmatched 為目標」，不新增需求。

**定稿前應先完成：**釐清單方證據、統一不去鹽模式、固定 A8/A9 唯一裁決、修正 A11，並拆清兩平台的錯誤／timeout／併發驗收。其餘架構與已定案範圍可維持。
